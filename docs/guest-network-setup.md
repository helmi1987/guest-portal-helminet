# Guest network setup (RouterOS 7) for the guest portal

Step-by-step preparation of a multi-site MikroTik RouterOS 7 network for a RADIUS-based captive
portal. This guide covers the **network side only**: VLAN, Wi-Fi (CAPsMAN), DHCP/DNS, firewall,
hotspot, RADIUS, central instance, DNS and certificates. The hotspot/RADIUS part of the RouterOS
script is generated by the application (admin UI, Sites section); this guide references it and
does not duplicate it.

Conventions: `<ANGLE_BRACKETS>` are placeholders. Example addresses are RFC 1918 and fictional.
Commands are given in RouterOS 7 slash syntax. Anything not checked against the vendor
documentation (manual.mikrotik.com, RouterOS 7.26) is marked **(to verify)**. Always test on one site before rolling out to all.

Comment keys: every object below that the setup assistant also creates carries its comment key
`guest-portal:<block>:<object>` (e.g. `comment="guest-portal:wifi:dp-guest"`), exactly as the generated
scripts set it. The scripts find, update and remove only objects with their key; an object with the same
name but without the key (manual setup without it, or assistant versions 0.6.0 to 0.12.6) makes their
`add` fail ("already exists" or "must use unique name"). The router state of the assistant shows such objects as "name taken (no
comment)" with a one-time command that sets the key, e.g.
`/caps-man datapath set [find where name="dp-guest" && !comment] comment="guest-portal:wifi:dp-guest"`.

Guided wizard (v0.19.0): the site page and the setup assistant link a step-by-step view of the same
blocks. Each step shows its inputs and commands and a "Check" that queries the router (read-only API,
§10c) and shows only that step's objects; "Next" is enabled when every router with API access shows
them as present, routers without API access are confirmed by hand ("Done manually"), any step can be
skipped. Order: router API access, RouterOS container (or "Not used (Docker host)", which counts as done),
guest network, Wi-Fi, firewall and option 114, hotspot/DNS/walled garden, router script (with certificate
checklist and RADIUS diagnostics; its check covers RADIUS, walled garden and certificate), hotspot pages, status.
The router script (RADIUS secret, certificate token) is only linked, never shown in the wizard; it comes after
the guest network steps because its hotspot part needs them.
Removal: setup assistant, "Remove everything again".

> Back up first on every router: `/system backup save name=pre-guest` and `/export file=pre-guest`.
> Use Safe Mode (Winbox/terminal `Ctrl+X`) while changing bridge VLAN filtering or firewall rules.

## 1. Overview and traffic matrix

```
 Guest phone --Wi-Fi (SSID, VLAN 30)--> CAP --trunk--> Router (bridge, VLAN 30 interface)
                                                         |  hotspot on vlan-guest, DHCP, DNS
                                                         |  RADIUS 1812/1813 --> portal instance
                                                         |  <-- Disconnect 3799 -- portal instance
                                        guest HTTPS 443 --> portal instance (walled garden)
```

| Flow | From | To | Port | NAT allowed? |
|---|---|---|---|---|
| Guest login page | guest VLAN | portal host | TCP 443 | Yes (source NAT of guest ok, see 7.4) |
| RADIUS auth/acct | site router (`src-address`) | portal instance | UDP 1812/1813 | **No** |
| Disconnect/CoA | portal instance | site router | UDP 3799 | **No** |
| Admin UI | admin/VPN network | portal instance | TCP 8443 | Optional |
| Account login (optional, 6.7) | portal instance | site's directory (AD / LDAP) | TCP 636 (or 389 StartTLS) | Yes |
| Internet | guest VLAN | WAN | any | Normal masquerade |

## 2. Per site: bridge and VLAN filtering

Assumes one bridge `bridge1` holds LAN ports and the trunk port(s) towards CAPs. The guest VLAN
interface must sit on **the bridge that contains the trunk port to the CAPs** (usually the LAN bridge),
never on a new, empty bridge: a VLAN interface on a bridge without ports receives nothing (no DHCP).
`/interface bridge port print where bridge=bridge1` must list the trunk port.

- `vlan-filtering=no` on that bridge: tagged frames from the trunk reach the VLAN interface without
  any bridge VLAN entry; only 2.4 is needed. Do not switch filtering on just for the guest VLAN.
- `vlan-filtering=yes`: the bridge drops VLAN 30 unless the bridge itself and the trunk port are
  tagged members (2.3). If filtering is already in use, only add the VLAN-30 entry.

The commands below show a full setup from scratch (new bridge with filtering).

```
# 2.1 Bridge (skip if it exists). Enable vlan-filtering LAST.
/interface bridge add name=bridge1 vlan-filtering=no

# 2.2 Ports. Trunk port(s) to CAPs carry VLAN 30 tagged; keep the management/LAN VLAN as you have it.
/interface bridge port add bridge=bridge1 interface=<TRUNK_PORT_TO_CAP> frame-types=admit-all ingress-filtering=yes

# 2.3 VLAN table: router (bridge1 itself) and trunk are tagged members of VLAN 30
/interface bridge vlan add bridge=bridge1 tagged=bridge1,<TRUNK_PORT_TO_CAP> vlan-ids=30 comment="guest-portal:net:bridge-vlan"

# 2.4 L3 interface for the guest VLAN on the bridge
/interface vlan add name=vlan-guest interface=bridge1 vlan-id=30 comment="guest-portal:net:vlan"

# 2.5 Enable filtering (use Safe Mode)
/interface bridge set bridge1 vlan-filtering=yes
```

Notes:
- If the CAP is a single-port device reached through a switch, add VLAN 30 as tagged on every hop (switch trunk ports, router port). A missing hop is the most
  common "no DHCP" cause.
- When the router itself is the CAPsMAN manager and CAPs forward locally, the trunk to each CAP must carry VLAN 30 tagged. With CAPsMAN-side forwarding (legacy
  `local-forwarding=no`) the tunnel carries the traffic and no trunk VLAN is needed (see 3.1).
- Management of the CAP itself stays on your existing management VLAN, never on VLAN 30.

Verify:
```
/interface bridge vlan print where vlan-ids=30
/interface bridge port print
/interface vlan print
```

## 3. Per site: Wi-Fi via CAPsMAN

Pick the subsection that matches the wireless package of the **CAPs and manager** at that site.
The two systems do not manage each other's devices: legacy `/caps-man` manages `wireless`
package CAPs, `/interface wifi` CAPsMAN manages `wifi` package CAPs. A site can run both.

Common settings for both: open guest SSID (no Wi-Fi password; access control is the portal),
client isolation on, VLAN 30 for the guest SSID only, the staff SSID untouched.

Optional Wi-Fi password: the setup assistant (step "Guest network", in the wizard "Guest Wi-Fi") can store a guest Wi-Fi password per site. By
default it stays on that instance only (encrypted with `APP_KEY`, not replicated); the checkbox
"Share with other instances" replicates it (encrypted with the federation data key). Other instances
only learn that the network has a password: without the password they print no Wi-Fi QR code, show a
hint in the assistant and leave `sec-guest` untouched in the generated script (never an open network).

### 3.1 Legacy CAPsMAN (v1, `/caps-man`, `wireless` package)

```
# Datapath: manager forwarding, guest traffic tagged with VLAN 30 by the manager,
# no client-to-client forwarding
/caps-man datapath add name=dp-guest bridge=bridge1 vlan-id=30 vlan-mode=use-tag \
    local-forwarding=no client-to-client-forwarding=no comment="guest-portal:wifi:dp-guest"

# Open security profile (no authentication-types = open network)
/caps-man security add name=sec-guest comment="guest-portal:wifi:sec-guest"

# Configuration: SSID, security, datapath; set country and channel settings as in your staff config
/caps-man configuration add name=cfg-guest ssid="Guest-WiFi" country=<COUNTRY> \
    security=sec-guest datapath=dp-guest comment="guest-portal:wifi:cfg-guest"

# Provisioning: create the guest SSID as a slave of your existing master configuration
# "set" replaces the list: include existing slaves (see print). The setup assistant's Wi-Fi block
# instead appends cfg-guest to the rules of the selected master configurations, keeping existing slaves;
# its uninstall (network) takes cfg-guest out of every rule again, the other slaves are kept.
/caps-man provisioning set [find where master-configuration=<MASTER_CFG>] \
    slave-configurations=cfg-guest
# Or create a new rule if none exists:
# /caps-man provisioning add action=create-dynamic-enabled master-configuration=<MASTER_CFG> \
#     slave-configurations=cfg-guest hw-supported-modes=an,gn,ac

/caps-man manager set enabled=yes
```

Notes:
- Recommended: `local-forwarding=no` (manager forwarding) together with datapath `bridge`, `vlan-mode=use-tag` and `vlan-id`. Traffic is tunneled to the manager
  and tagged there. With `local-forwarding=no`, the MAC addresses of the CAPs must be unique.
- With `local-forwarding=yes` CAPsMAN has no control over forwarding, and the datapath VLAN settings are not documented to apply. VLAN tagging must then be
  configured on the CAP side (`/interface wireless cap set bridge=<CAP_BRIDGE>` plus bridge VLAN setup on the CAP) **(to verify)**.
- `vlan-mode=use-tag` with `vlan-id=30` tags guest frames on egress and strips on ingress.
- Client isolation is the datapath setting `client-to-client-forwarding=no`. It only isolates clients within one interface; see the cross-radio note below.
- Slave configurations only work if the radio supports multiple SSIDs (virtual AP).

Verify:
```
/caps-man interface print
/caps-man registration-table print
/interface bridge port print where interface~"cap"     # dynamic CAP ports in bridge1
```
On a phone: SSID visible; after connecting, `/caps-man registration-table print` shows the client.

### 3.2 New CAPsMAN (`wifi` package, `/interface wifi`, a.k.a. CAPsMAN v2; formerly `wifiwave2`)

```
# Datapath: bridge + VLAN id, client isolation
/interface wifi datapath add name=dp-guest bridge=bridge1 vlan-id=30 client-isolation=yes comment="guest-portal:wifi:dp-guest"
# wifi-qcom-ac CAPs: do NOT set vlan-id (no VLAN offload); set PVID 30 on the CAP's bridge port

# Open security (no authentication-types)
/interface wifi security add name=sec-guest comment="guest-portal:wifi:sec-guest"

# Configuration: SSID, country, datapath, security
/interface wifi configuration add name=cfg-guest ssid="Guest-WiFi" country=<COUNTRY> \
    security=sec-guest datapath=dp-guest comment="guest-portal:wifi:cfg-guest"

# Provisioning: add the guest SSID as slave of your existing master configuration
# "set" replaces the list: include existing slaves (see print). The setup assistant's Wi-Fi block
# instead appends cfg-guest to the rules of the selected master configurations, keeping existing slaves;
# its uninstall (network) takes cfg-guest out of every rule again, the other slaves are kept.
/interface wifi provisioning set [find where master-configuration=<MASTER_CFG>] \
    slave-configurations=cfg-guest
# Or new rule:
# /interface wifi provisioning add action=create-dynamic-enabled \
#     master-configuration=<MASTER_CFG> slave-configurations=cfg-guest supported-bands=2ghz-n
# (one rule per band: all listed bands must be supported by the radio; repeat with 5ghz-ac)

# Manager (if not yet enabled)
/interface wifi capsman set enabled=yes
```

Notes:
- The package was renamed from `wifiwave2` to `wifi` in RouterOS 7.13. Today's packages are `wifi-qcom` and `wifi-qcom-ac`.
- Default `traffic-processing` is `on-cap` (local forwarding on the CAP). `traffic-processing=on-capsman` exists only from 7.21beta2 and not for `wifi-qcom-ac`.
- `vlan-id` in the datapath must NOT be set for `wifi-qcom-ac` CAPs (no VLAN offload); set the PVID on the CAP's bridge port instead. Do not add the dynamic
  interfaces with `bridge port add interface=all`.
- `client-isolation` as a datapath property in the `wifi` package: **(to verify)**. It only isolates clients within one interface; see the cross-radio note
  below.
- With the CAP forwarding locally, the CAP's bridge name must match `bridge=` of the datapath, and the CAP puts the guest interface into that bridge as untagged
  member of VLAN 30 (PVID 30); the trunk port must be tagged for VLAN 30 (section 2) **(to verify)**.
- CAP side (on each CAP): `/interface wifi cap set enabled=yes discovery-interfaces=<IF> caps-man-addresses=<MANAGER_IP>` (or discovery via layer 2).
  Certificates between manager and CAP are required unless `require-peer-certificate=no` **(to verify)**.

Verify:
```
/interface wifi capsman remote-cap print
/interface wifi registration-table print
/interface bridge port print            # dynamic wifi ports show PVID 30
```

### 3.3 Isolation across radios and APs
`client-isolation` / `client-to-client-forwarding=no` only isolates clients within one wireless
interface. Clients on different radios or APs of the same guest VLAN can still reach each other
through the bridge. Add bridge filter rules for the guest VLAN (drop guest-to-guest forwarding
between the CAP ports), or set bridge port `horizon` on the CAP side **(to verify, forum-based)**.

### 3.4 Mixed sites

Create both sets side by side (the names `dp-guest`, `cfg-guest` exist in separate menus).
Use the same SSID and VLAN so guests roam between old and new APs. Roaming does not preserve the
hotspot session if the client IP changes, but the VLAN/subnet is the same so it normally does.

The setup assistant (v0.19.0) takes several Wi-Fi modes at once (step "Guest network", in the wizard "Guest Wi-Fi": tick every mode
the site uses):
the Wi-Fi block then has one part per mode and creates `dp-guest`, `sec-guest` and `cfg-guest` once per
package (`/caps-man` and `/interface wifi`; CAPsMAN of the wifi package and a local radio share them).

Switching modes (for example from CAPsMAN to a local radio): the Wi-Fi block of the new selection does not
remove what the earlier one created, so `cfg-guest` stays in your provisioning rules (and the own per-CAP
rules stay) and the CAPs keep broadcasting the guest SSID. Query the router state after saving the new
modes: the assistant lists these objects as "left over" and shows, per router, a clean-up block (step
"Guest network", in the wizard "Guest Wi-Fi"). It takes `cfg-guest` out of the rules of the deselected
CAPsMAN package and removes only objects with the assistant's comment keys; run it once, then query the
state again. By hand, the same commands are in the network uninstall of the old mode.

### 3.5 Guest SSID only on some CAPs, provisioning rules

Setup assistant, step "Guest network" (wizard: "Guest Wi-Fi"), per CAPsMAN mode (optional): tick the CAP radios (radio-mac, from the router
state) that get the guest SSID. Per radio the Wi-Fi block adds an own provisioning rule
(`radio-mac=<mac>`, comment `guest-portal:wifi:cap-<mac>`) before your rule that provisions the radio now,
copying it plus `cfg-guest`; your rules then do not get `cfg-guest`. Verified with the wifi package; legacy
CAPsMAN untested on hardware.

The assistant also shows the provisioning rules of each router with a state query (master and slave
configurations editable, new rules with band, master and slaves) and generates a script for the changes:
it changes a rule only while it still has the values read by the query and adds a new rule only when none
with the same band and master exists. Nothing is stored. CAPsMAN applies rule changes to the CAPs; if a
CAP did not pick them up, check `/interface wifi provisioning print` (or `/caps-man provisioning print`)
and provision that CAP manually. The scripts never provision: provisioning a CAP without a matching rule
can remove its configuration.

## 4. Per site: addressing, DHCP and DNS

```
/ip address add address=10.30.0.1/24 interface=vlan-guest comment="guest-portal:net:gateway"
/ip pool add name=guest-pool ranges=10.30.0.10-10.30.0.250 comment="guest-portal:net:pool"
/ip dhcp-server add name=guest-dhcp interface=vlan-guest address-pool=guest-pool \
    lease-time=30m disabled=no comment="guest-portal:net:dhcp-server"
/ip dhcp-server network add address=10.30.0.0/24 gateway=10.30.0.1 dns-server=10.30.0.1 comment="guest-portal:net:dhcp-network"
```

- Lease time: short, e.g. 30m-1h, so the pool recovers from many one-time visitors. Do not go below ~10 min (renewal chatter and captive-portal re-detection).
- A /24 holds ~240 devices; use a /23 where events are expected.
- DNS: the router serves guests so hotspot DNS interception works and the portal name can be pinned (section 8.1). Do not hand out public resolvers directly.

```
/ip dns set allow-remote-requests=yes servers=<UPSTREAM_DNS_1>,<UPSTREAM_DNS_2>
```
`allow-remote-requests=yes` is required; it must be protected by the firewall (section 5) so it is
not an open resolver on WAN. `/ip hotspot setup` normally creates pool and DHCP server for you;
the manual commands above are equivalent. Whether `/ip hotspot` should use `address-pool=none`
if the DHCP server already hands out addresses: **(to verify)**; the generated script uses
`address-pool=<GUEST_POOL>`, follow it.

Verify:
```
/ip dhcp-server lease print where server=guest-dhcp
/ip dns print
```
Phone: connects, gets 10.30.0.x, gateway and DNS 10.30.0.1.

### 5.2 Address lists
```
/ip firewall address-list
add list=PORTAL address=<PORTAL_IP> comment="guest-portal:fw:addr-portal"
add list=PORTAL_RADIUS address=<PORTAL_IP> comment="guest-portal:fw:addr-radius"
add list=RFC1918 address=10.0.0.0/8 comment="guest-portal:fw:addr-rfc1918-10"
add list=RFC1918 address=172.16.0.0/12 comment="guest-portal:fw:addr-rfc1918-172"
add list=RFC1918 address=192.168.0.0/16 comment="guest-portal:fw:addr-rfc1918-192"
```

### 5.3 Input chain (guest -> router)

Guests may only use DHCP, DNS and the hotspot's own pages. Place these rules **before** your
existing "drop all not from LAN" rule, and after the established/related accept.

```
/ip firewall filter
add chain=input action=accept in-interface-list=GUEST protocol=udp dst-port=67 comment="guest-portal:fw:in-dhcp"
add chain=input action=accept in-interface-list=GUEST protocol=udp dst-port=53 comment="guest-portal:fw:in-dns"
add chain=input action=accept in-interface-list=GUEST protocol=tcp dst-port=53 comment="guest-portal:fw:in-dns-tcp"
add chain=input action=accept in-interface-list=GUEST protocol=icmp limit=10,20:packet comment="guest-portal:fw:in-ping"
add chain=input action=accept protocol=udp src-address-list=PORTAL_RADIUS dst-port=3799 comment="guest-portal:fw:in-coa"
add chain=input action=drop in-interface-list=GUEST comment="guest-portal:fw:in-drop-mgmt"
```
- Hotspot inserts dynamic rules (hotspot chain) for its own login/redirect ports (commonly TCP 80, 443, 64872-64875 **(to verify)**) at the top of
  input/forward/NAT; they are evaluated before your static rules. If the login page is unreachable only after adding the drop rule, look at `/ip firewall filter
  print dynamic`. The port list and the dynamic rules are not documented **(to verify)**.
- The Disconnect rule is needed on every router; the source is the portal instance IP **as seen by the router** (the container/Docker host IP, no NAT, see 7).
- Place a rule for RADIUS replies only if your input policy drops everything else: replies to requests initiated by the router are covered by
  `established,related`.

### 5.4 Forward chain (guest -> elsewhere)

Order matters. Insert before your generic rules (use `place-before=0` or `move`). `add` appends at the
end of a chain, after an existing drop rule; the setup assistant's firewall block (v0.12.6) moves its
`guest-portal:fw:` rules (`guest-portal: ` before 2026-10-31) of input and forward before the first static
rule that is not its own, keeping their order. Check with `/ip firewall filter print where comment~"guest-portal"` and
`/ip firewall filter print where chain=input || chain=forward`: they must come before any drop rule.

```
/ip firewall filter
add chain=forward action=accept connection-state=established,related in-interface-list=GUEST comment="guest-portal:fw:fwd-from-guests"
add chain=forward action=accept connection-state=established,related out-interface-list=GUEST comment="guest-portal:fw:fwd-to-guests"
add chain=forward action=accept in-interface-list=GUEST dst-address-list=PORTAL protocol=tcp dst-port=443 comment="guest-portal:fw:fwd-portal"
add chain=forward action=drop in-interface-list=GUEST dst-address-list=RFC1918 comment="guest-portal:fw:fwd-drop-lan"
add chain=forward action=drop out-interface-list=GUEST in-interface-list=!GUEST connection-state=new comment="guest-portal:fw:fwd-drop-new"
add chain=forward action=accept in-interface-list=GUEST out-interface-list=WAN comment="guest-portal:fw:fwd-internet"
```
- The stateful accepts cover guest traffic only: a generic established/related accept above the defconf
  FastTrack rule would turn off FastTrack for all traffic.
- FastTrack (defconf `fasttrack-connection`) may bypass the hotspot for fasttracked connections
  **(assumption, to verify)**. The guest stateful accepts come before it, so guest connections are not
  fasttracked. Otherwise exclude the guest list in the FastTrack rule
  (`in-interface-list=!GUEST out-interface-list=!GUEST`) or keep FastTrack off for guests.
- The portal rule comes before the RFC 1918 drop because the portal IP is private (RFC 1918).
- Guest->guest on the same L2 never passes the router; that is what client isolation (section 3) handles. Guest->guest across sites is blocked by rule 3
  (private ranges).
- Before login the hotspot already drops everything except the walled garden; the same rules apply after login, so the portal stays reachable (re-login, logout
  page).
- NAT: guests need `masquerade` out of WAN as usual (`/ip firewall nat add chain=srcnat out-interface-list=WAN action=masquerade`). Make sure masquerade does
  **not** apply to RADIUS/Disconnect or tunnel traffic (see 7.3).

Verify:
```
/ip firewall filter print stats
```
Counters of the guest rules rise when a phone is connected. From a guest phone, the router's
Winbox/WebFig/SSH ports and a LAN address must time out.

## 6. Per site: hotspot on the guest VLAN

### 6.1 Certificate for the hotspot host name
Place the wildcard certificate for the hotspot host names on the instance as `/data/certs/router.crt` (PEM, full chain)
and `/data/certs/router.key` (section 8.2). The script generated in Admin → Sites adds a scheduler entry (at startup and daily)
that downloads the certificate from the instance with a per-router token, imports it only when the fingerprint changed and sets
`ssl-certificate` in the hotspot profile `guest-portal` (certificate name `guest-portal`).
- The download (`https://<PORTAL_HOST>/router-cert/...`, TCP 443) is sent with `src-address=<router IP>`; the instance accepts it
  only from the router IP registered for that router (plus the token). So TCP 443 from the router's router IP to the portal must be
  routed without NAT and allowed on the central firewall (section 7.2/7.3). Denied downloads are logged by the instance.
  The IP check stays on with a reverse proxy (`TRUSTED_PROXIES`, only the proxy's address; `*` or a `/0` network is ignored and
  logged as an error at start); only `PORTAL_ROUTER_IP_CHECK=false` switches it off (needed only if the routers reach the guest
  port through a proxy or NAT, which is not recommended). The former `PORTAL_ROUTER_CERT_CHECK_IP` is no longer read.
- The portal certificate must be publicly trusted: the fetch uses `check-certificate=yes`.

> **Critical fix in v0.12.5:** v0.12.5 fixes a critical bug in the router certificate script of
> v0.12.1-v0.12.4 that could delete all certificates on the router (e.g. CAPsMAN). The script of v0.12.0
> and earlier had the same bug (`:local name` with `/certificate remove [find where name=$name]`).
> Cause: inside `find where`, a local named like a property is not substituted, so `name=$name`
> matches every item. Disable or replace the scheduler `guest-portal-cert` on every router
> (`/system scheduler disable [find where name="guest-portal-cert"]`) and run the router script of
> v0.12.5 again (it replaces the script and the scheduler).
> The same bug made `/ip hotspot profile find where name=$name` match every profile, so the first
> hotspot profile may have received `ssl-certificate`/`login-by`: check `/ip hotspot profile print`.

How the certificate script identifies certificates (the chain PEM creates one certificate per PEM
block: leaf + intermediate/root CAs):
- The current certificate is the one set as `ssl-certificate` on the profile `guest-portal` (renaming it
  does not matter); its fingerprint is compared with `/router-cert/<id>/fingerprint` (lowercase hex
  SHA-256 without colons; both sides are normalised, RouterOS format **(to verify)**).
- RouterOS certificates have no `comment` property, so certificates are identified by name only.
  Imported certificates get the temporary name `guest-portal-import*`; the leaf is the one whose
  fingerprint matches (fallback: the one with the private key). Before the import, previous CAs
  (`guest-portal-ca-<n>`, regex `^guest-portal-ca-[0-9]+$`) and legacy names (`guest-portal-new`,
  `guest-portal-new_*`) are removed, except the certificate in use. The profile is then switched to the
  new leaf, the previous `guest-portal` leaf is removed, the leaf is renamed to `guest-portal` and the
  CAs to `guest-portal-ca-<n>`. Certificates with other names are never touched (a previous certificate
  renamed by you stays; remove it manually).
- Removal (v0.12.5): no `find` filter and no computed expression is passed to `/certificate remove`.
  The script walks all certificates, checks each name with explicit string comparisons (exactly
  `guest-portal`, `guest-portal-ca-` followed by digits only, `guest-portal-new`, prefix
  `guest-portal-new_`, prefix `guest-portal-import`) and removes matching ones by id. Certificates
  referenced as `ssl-certificate` by any hotspot profile are never removed. If more than 10
  certificates would be removed, nothing is removed and an error is logged.
- Script locals are prefixed `gp` (`gpName`, `gpTmp`, ...): inside `find where`, a local named like a
  property (e.g. `name`) is not substituted, so `name=$name` matches every item.
- Errors are logged with the failing step (`:onerror`, RouterOS >= 7.13 **(to verify)**):
  `/log print where message~"guest-portal"`.
- **Secrets in the log:** RouterOS writes the full source of a script added or changed via `/system script`
  (including the RADIUS secret and the download token) to the system log. Paste the generated script
  into the terminal instead of saving it as a `/system script`, or clear the log afterwards. The
  certificate script is itself a `/system script` holding the token, so check the log after running the
  generated script.

Manual import (troubleshooting only):
```
/certificate import file-name=router.crt passphrase=""
/certificate import file-name=router.key passphrase=""
/certificate print     # the leaf certificate shows flag K (private key)
```

### 6.2 DNS name for the hotspot host
The hotspot name is the router's own HTTPS login name and resolves to the guest gateway; the portal
name is the portal instance. They must differ (the admin UI rejects a hotspot host equal to the portal
host). Guests must resolve the hotspot name to the router's guest address. No own entry is needed: the
hotspot adds a dynamic A entry (flag D) for the `dns-name` of its profile to the hotspot address
(decision 2026-11-02). An own static entry of earlier versions makes nothing better; remove it (dynamic
entries cannot be removed and are never touched):
```
/ip dns static print where name=hotspot-a.guest.example.com
/ip dns static remove [find where comment="guest-portal:dns:hotspot-name" && !dynamic]
```
If the guest network gets IPv6 and the hotspot name has a public AAAA record, the router does not cover
AAAA for it.

### 6.3 Hotspot: setup wizard or manual
- **Manual (recommended, reproducible):** paste the script generated in **Admin -> Sites -> (site) -> RouterOS script**. It creates the RADIUS client, `/radius
  incoming`, hotspot profile and hotspot server `guest-portal` (`use-radius=yes`, `login-by=https,mac`; `mac` for the MAC whitelist), walled garden and the certificate
  script/scheduler (6.1). Fill its `<PLACEHOLDERS>` from the worksheet: `<HOTSPOT_GATEWAY_IP>` = 10.30.0.1,
  `<GUEST_INTERFACE>` = `vlan-guest`, `<GUEST_POOL>` = `guest-pool`.
  Hotspot and profile use the name `guest-portal`, all other entries a comment key `guest-portal:<block>:<object>`
  (e.g. `guest-portal:radius:server`; older versions: comment `guest-portal`); the script removes them first, so it can be re-run (re-running
  recreates the hotspot and logs out connected guests). Do not rename the profile: the certificate script sets
  `ssl-certificate` on the profile named `guest-portal`.
- **Wizard:** `/ip hotspot setup` asks for interface, address, pool, certificate, SMTP, DNS and a local user. Use it only if you then align the result with the
  generated script (set `use-radius=yes`, `login-by=https,mac`, remove the local test user, no `trial`). The wizard also adds firewall/NAT rules of its own (not
  described in the docs **(to verify)**); check `/ip firewall filter print` and `nat print` for duplicates **(to verify)**.

### 6.4 Upload the hotspot pages
The portal generates four pages of the hotspot HTML directory (since v0.29.0; before only `login.html`). Each is a
meta refresh plus a link, no JavaScript. RouterOS replaces the `$(...)` variables when it serves a page (variables
verified against the default pages of a RouterOS 7.24.5 CHR); `-esc` variants are URL-encoded.

| File | RouterOS shows it | Sends the browser to |
|---|---|---|
| `login.html` | to a device that is not logged in | `<portal>/portal?site=<id>&mac=$(mac-esc)&ip=$(ip)&link-login-only=$(link-login-only-esc)&link-orig=$(link-orig-esc)` (login page) |
| `status.html` | to a logged-in device that opens the hotspot name (e.g. the iOS captive sheet again) | `<portal>/portal/status?site=<id>&mac=$(mac-esc)&ip=$(ip)&link-login-only=$(link-login-only-esc)`: the portal status page of the device's open session (remaining time, usage, "Log out"); without an open session the login page |
| `logout.html` | after a logout on the router (e.g. its logout link) | `<portal>/portal?site=<id>&mac=$(mac-esc)&ip=$(ip)&link-login-only=$(link-login-only-esc)`: the login page with the notice "You have logged out" |
| `alogin.html` | right after a successful login | `$(link-redirect)` at once, the portal status page (the `dst` of the login); the RouterOS default waits 2 s and may open a status popup |

Other default files (`rlogin.html`, `redirect.html`, `error.html`, `radvert.html`, `xml/`, CSS, images, `md5.js`) stay
the RouterOS defaults. The pages must not contain `$(` except these variables (RouterOS reads every `$(` as a
variable or directive).

1. Download the four files from the admin UI (site page, router configuration, setup assistant step "Hotspot pages").
2. Upload them into the hotspot HTML directory of the router, replacing the default files. The
   generated profile sets `html-directory` from the setup assistant field "Hotspot HTML directory":
   `hotspot` (RouterOS default) or `flash/hotspot` for devices with a flash folder; choose the value
   shown by `/ip hotspot profile print where default=yes`. The fetch block of the assistant writes
   `<html-directory>/login.html`, `status.html`, `logout.html` and `alogin.html` (route
   `/router-login/<router>/<page>.html`, router token and router IP like the certificate download).
   `html-directory-override` exists as an alternative. RouterOS
   creates the default files when a hotspot with a new html-directory starts (verified on CHR). Resetting the pages:
   `/ip hotspot reset-html` is not in the official docs (documented: Winbox button
   IP > Hotspot > Reset HTML) **(to verify the CLI command)**.
   The fetch block is one `{ ... }` block (v0.30.0): paste it whole, RouterOS then runs the fetches one after
   another (pasted as single lines the terminal does not wait for `/tool fetch` and the following lines get lost).
   At the end it prints one line per page, `ok login.html (<size> bytes)` or `MISSING login.html`; a failed fetch
   prints `FAILED fetch <page>.html` and the block goes on.
3. Methods: the fetch block of the setup assistant, Winbox -> Files drag & drop, `/tool fetch` from an internal
   HTTP(S) server, or SFTP. Example: `/tool fetch url="https://<INTERNAL_FILE_HOST>/status.html" dst-path=hotspot/status.html`.
4. Re-upload the four pages after every change of portal URL or site id in the admin UI; the portal shows
   "Update router" for routers whose pages are outdated (section 10d).

### 6.5 RADIUS client and incoming
The generated script contains `/radius add address=<INSTANCE_IP> secret=... service=hotspot
src-address=<ROUTER_IP_SEEN_BY_PORTAL>` and `/radius incoming set accept=yes port=3799`. Always set `port=3799` explicitly: the manual
names 1700 as the default port, and `accept` defaults to `no`. Check that:
- `address` is the portal instance IP (not a NAT front address, see 7.3),
- `src-address` is the router address you registered as Router IP in the admin UI (the address the portal sees), reachable from the portal in both directions,
- the secret equals the one shown in the admin UI for this router.
- Whether `/radius incoming` validates the source IP of incoming requests against the `/radius` entries is not documented **(to verify)**.
- **RouterOS >= 7.15:** `/radius` has `require-message-auth` (default `yes-for-request-resp`). The portal's FreeRADIUS sends Message-Authenticator. If logins
  fail with RADIUS errors, check this setting first. Do not disable it except temporarily for troubleshooting.
- Walled garden IP entries: use `/ip hotspot walled-garden ip add action=accept ...`; the docs are ambiguous (`accept` / `allow`) **(to verify)**.
- `/ip hotspot walled-garden print` also lists every IP walled-garden entry as a dynamic copy (flag `D`, same comment, its
  `dst-address` and `dst-port`); RouterOS refuses to edit or remove it, it follows its IP entry. An IP entry with the comment of
  earlier versions (`guest-portal` / `guest-portal: ...`) shows as "legacy" in the router state of the assistant: run the router
  script once, it replaces the entry with the keyed one and the copy follows (verified on a RouterOS 7.24.5 CHR).

Verify:
```
/ip hotspot print
/ip hotspot profile print
/ip hotspot walled-garden print
/ip hotspot walled-garden ip print
/radius print
/radius incoming print
/radius monitor 0 once          # counts of requests/accepts/rejects/timeouts
```
Test with a phone: join the guest SSID, open any plain `http://` address, e.g. `http://example.com` (or the OS captive portal
popup). Expected: redirect to the portal page, then login, then internet.
```
/ip hotspot host print                 # client appears (unauthorized -> authorized after login)
/ip hotspot active print               # session with user = one-time token
/log print where topics~"radius" or topics~"hotspot"
```
(Use `/log/print` if a topic filter requires it; enable debugging if needed:
`/system logging add topics=radius,debug action=memory`, remove it after the test.)

### 6.6 Walled garden for social login
When social login is switched on and a provider is configured (admin settings, CONCEPT.md §7.2 D), the
guest must reach the provider's sign-in pages before the hotspot login. The router script adds one
`/ip hotspot walled-garden` entry (`dst-host`, `action=allow`) per host of every configured provider,
with the comment key `guest-portal:walled:social-<host>` (`*` written as `any`, `.` as `-`). It first
removes the own entries of all providers by their exact keys, so a provider that is switched off loses
its entries on the next run; entries of others are never changed. The router state query shows missing
entries (and own entries of providers no longer offered) as "apply" lines.

| Provider | Hosts |
|---|---|
| Google | `accounts.google.com`, `*.googleusercontent.com`, `*.gstatic.com`, `apis.google.com`, `oauth2.googleapis.com`, `www.googleapis.com`, `play.google.com` (Android captive portal browser), `fonts.googleapis.com` |
| Apple | `appleid.apple.com`, `appleid.cdn-apple.com`, `idmsa.apple.com`, `gsa.apple.com`, `*.cdn-apple.com` |
| Facebook | `*.facebook.com`, `*.fbcdn.net`, `*.facebook.net`, `*.fbsbx.com` |
| GitHub | `github.com`, `*.github.com`, `*.githubassets.com`, `*.githubusercontent.com` |

The list lives in `app/Auth/Social/WalledGarden.php`. Providers change the hosts their sign-in pages load
from: when a sign-in page stays blank or half-loaded before login, check the blocked hosts in the browser's
developer tools and extend the list **(to verify per provider on real devices)**. Federation limited mode
does not change the entries. Re-run the router script after switching social login or a provider on or off.
Captive-portal mini browsers may not open the provider pages at all (Google refuses embedded web views):
the social login page tells the guest to close the mini browser and open any website in the normal browser (the hotspot redirects to the portal again).

### 6.7 Account login: the portal must reach the directory
With the account login (user name and password of the site's Active Directory / LDAP, site page →
"User account", CONCEPT.md §7.2 E) the guest's browser only talks to the portal; the portal checks the
password with an LDAP bind against the site's directory. The hotspot and walled garden need no change.
The **portal instance** (container or Docker host) must reach the directory server: allow TCP 636 (LDAPS,
recommended) or 389 (StartTLS) from the portal's address to the domain controller or LDAP server, across the
VPN when the portal runs centrally (section 7), and nothing from the guest network. The server's certificate
must carry the host name entered on the site page (a domain controller certificate from the AD certificate
services usually does; paste the root CA on the site page when it is an internal CA). The service account
needs read access only (an ordinary domain user, no administrator). The "Check" button on the site page
tests reachability, TLS, the service account and the user search.

## 7. Central instance and inter-site connectivity

The portal instance sits in one central network (e.g. at site A). Sites reach it through the existing
site-to-site VPN/routing.

### 7.1 Why RADIUS must keep the real router IP
FreeRADIUS accepts requests only from known clients, identified by source IP plus shared secret
(CONCEPT section 2.2). The portal also stores the router IP per router and sends Disconnect requests
to that address. If a router's traffic is masqueraded or source-NATed on its way:
- the portal sees a different IP -> request dropped silently ("unknown client"), or two routers collapse into one address and secrets/NAS records collide,
- Disconnect is sent to the router IP of the router, but the router only accepts Disconnect from the addresses of its configured `/radius` entries, so
  replies/requests with the wrong source fail.

So: no masquerade/srcnat on the VPN interface or between site LAN and the portal network, for
UDP 1812, 1813 and 3799. Set `src-address` in `/radius` to a stable address of the router that is
routed through the tunnel (a LAN or loopback-bridge address), and register exactly that address
in the admin UI.

### 7.2 Option 1: RouterOS container on a central router (x86/arm64)
Details: `docs/routeros-container.md`. Summary of the network part:
```
/interface veth add name=veth-portal address=172.17.0.2/24 gateway=172.17.0.1 comment="guest-portal:container:veth"
/interface bridge add name=containers comment="guest-portal:container:bridge"
/interface bridge port add bridge=containers interface=veth-portal comment="guest-portal:container:bridge-port"
/ip address add address=172.17.0.1/24 interface=containers comment="guest-portal:container:gateway"
```
- Container setup on the router (names as in the RouterOS 7 docs):
  - Device mode: `/system/device-mode/update container=yes` needs physical confirmation (reset button or cold boot within 5 minutes; a normal reboot aborts it).
  - Registry: `/container/config set registry-url=<URL> username=<USER> password=<PASS>`.
  - Mounts and env: `/container/mounts add list=<LIST> src=<SRC> dst=<DST>`, `/container/envs add list=<LIST> key=<KEY> value=<VALUE>`.
  - `/container/add` references them with `mountlists=<LIST>` and `envlist=<LIST>` (not `mounts`/`envlists`).
- **Isolate the container network:** the `containers` bridge is not in LAN/WAN lists; put it in an interface list `CONTAINERS` and filter explicitly (below).
  The container must not reach LAN or management services except what it needs (DNS, outbound to the sites' UDP 3799, HTTPS for SMS/cert API if used).
- **Preferred: routing without NAT.** Announce 172.17.0.0/24 to the sites (static routes via the tunnel, or add it to the tunnel's allowed/remote networks). The
  portal IP is then 172.17.0.2 and the container sees real router IPs. Disconnect leaves the container with source 172.17.0.2, which is the `/radius` `address`
  on the sites.
- **Alternative: dst-nat on the central router** (portal reachable at a LAN IP):
```
/ip firewall nat
add chain=dst-nat action=dst-nat dst-address=<CENTRAL_LAN_IP> protocol=tcp dst-port=443  to-addresses=172.17.0.2 to-ports=443
add chain=dst-nat action=dst-nat dst-address=<CENTRAL_LAN_IP> protocol=tcp dst-port=8443 to-addresses=172.17.0.2 to-ports=8443 src-address-list=ADMIN_NET
add chain=dst-nat action=dst-nat dst-address=<CENTRAL_LAN_IP> protocol=udp dst-port=1812,1813 to-addresses=172.17.0.2
```
  dst-nat keeps the client's source IP, so RADIUS still sees the real router IP; replies go back
  via conntrack. The Disconnect direction is the problem: the sites expect it from the `/radius`
  address (`<CENTRAL_LAN_IP>`), so add `srcnat action=src-nat to-addresses=<CENTRAL_LAN_IP>
  src-address=172.17.0.2 protocol=udp dst-port=3799`. This works but is more fragile than
  routing; prefer the routed option **(to verify, whether `/radius incoming` checks the source
  address like this on your RouterOS version)**.

Central router firewall (forward chain), example:
```
/ip firewall filter
add chain=forward action=accept protocol=udp dst-address=172.17.0.2 dst-port=1812,1813 src-address-list=SITE_ROUTERS comment="RADIUS from routers"
add chain=forward action=accept protocol=udp src-address=172.17.0.2 dst-port=3799 dst-address-list=SITE_ROUTERS comment="Disconnect to routers"
add chain=forward action=accept protocol=tcp dst-address=172.17.0.2 dst-port=443 src-address-list=GUEST_SUBNETS comment="guest portal port"
add chain=forward action=accept protocol=tcp dst-address=172.17.0.2 dst-port=443 src-address-list=SITE_ROUTERS comment="router certificate download"
add chain=forward action=accept protocol=tcp dst-address=172.17.0.2 dst-port=8443 src-address-list=ADMIN_NET comment="admin port"
add chain=forward action=accept src-address=172.17.0.2 out-interface-list=WAN comment="container: internet"
add chain=forward action=drop in-interface=containers comment="container: nothing else"
add chain=forward action=drop out-interface=containers comment="to container: nothing else"
```
`SITE_ROUTERS` = the routers' `src-address` values, `GUEST_SUBNETS` = all guest subnets,
`ADMIN_NET` = your admin/VPN network. The stateful accept rule for `established,related` must
come first. Memory: reserve about 512 MB for the container.

### 7.3 Option 2: Docker host (e.g. a NAS)
- Run the image as in [docker-host.md](docker-host.md) (compose file, network mode). Publish `443/tcp`, `8443/tcp`, `1812/udp`, `1813/udp`; mount `/data` (certificates in `/data/certs`).
- Give the host a fixed LAN IP (the portal IP). Docker's published UDP ports keep the sender's source IP with iptables DNAT; verify with `tcpdump` or the
  portal's RADIUS log. Do not use a userland proxy or a reverse proxy in front of UDP **(to verify on your Docker setup)**.
- Outgoing Disconnect from the container is masqueraded by Docker to the host IP, which is the address your routers have in `/radius`. Good: this is the
  expected source.
- Firewall of the host/NAS: allow 443 from guest subnets and site routers (certificate download), 8443 from admin network, 1812/1813 UDP from
  site routers only; block the rest.

### 7.4 Guest traffic to the portal across the VPN
Guests (10.30.0.x) connect to the portal on TCP 443. Choose one:
- Add all guest subnets to the tunnel's allowed networks (IPsec policy / WireGuard `allowed-address` / route) and allow them on the central firewall (done
  above), or
- Source-NAT guest -> portal at the site router to its tunnel address: `/ip firewall nat add chain=srcnat src-address=10.30.0.0/24 dst-address=<PORTAL_IP>
  protocol=tcp dst-port=443 action=src-nat to-addresses=<ROUTER_IP_SEEN_BY_PORTAL>`. This is acceptable for the web part only; the portal binds access to the
  MAC reported by RADIUS (`Calling-Station-Id`), not to the web client IP (CONCEPT section 5). Never apply it to UDP.
Alternatively expose the guest port publicly (dst-nat from WAN); then the walled garden must
use the public IP and DNS must resolve publicly. Not covered here.

Verify (from a site router):
```
/ping <PORTAL_IP> src-address=<ROUTER_IP_SEEN_BY_PORTAL>
/tool fetch url="https://portal.example.com/" mode=https check-certificate=yes output=none
/radius monitor 0 once
```

## 8. DNS and certificates

### 8.1 DNS names
| Name | Resolves to | Where |
|---|---|---|
| `portal.example.com` | `<PORTAL_IP>` (internal) | Public DNS A record (needed for DNS-01 and external resolution), plus static entry on every site router |
| `hotspot-a.guest.example.com` | 10.30.0.1 (router in VLAN) | Router static DNS; public record optional |

Many upstream/ISP resolvers drop answers with private addresses ("DNS rebinding protection"), so
pin both names on each router. Pin the portal name as CNAME to an internal name with a static A record
(the setup assistant generates this):
```
/ip dns static add name=guest-portal-v4.internal address=<PORTAL_IP> comment="guest-portal:dns:portal-a"
/ip dns static add name=portal.example.com type=CNAME cname=guest-portal-v4.internal comment="guest-portal:dns:portal-cname"
:put [:resolve portal.example.com]                          # IPv4 address
:put [:resolve domain-name=portal.example.com type=ipv6]    # "no appropriate record"
```
Why: a plain static A entry covers only A queries; AAAA queries still go upstream. If public DNS has an
AAAA record (e.g. a wildcard `*.example.com`), the router's `/tool fetch ... src-address=<IPv4>` picks
IPv6 and fails with "Address family not supported by protocol" (certificate script, hotspot pages fetch).
With the CNAME the router answers AAAA with "no appropriate record". A static `type=NXDOMAIN` entry is
not an alternative: it blocks the A record too.

`<PORTAL_IP>` (site setting "Portal IP") is the portal instance as reachable from the router, e.g. the
Docker host or container IP; usually empty (= instance IP for RADIUS). Never the guest gateway or an
address inside the guest subnet (the admin UI rejects both).
The walled garden entry `dst-host=portal.example.com` (generated) lets guests resolve and reach it
before login; the IP-based walled garden entry covers the destination IP.

### 8.2 Certificates (DNS-01)
Two certificates, both publicly trusted, issued with the DNS-01 challenge because the hosts
resolve to private addresses (HTTP-01 is impossible):
1. `portal.example.com` for the instance (guest port 443 and admin port 8443).
2. A wildcard `*.guest.example.com` for the router hotspot names (`hotspot-a.guest.example.com`, ...),
   so one certificate serves all sites (CONCEPT section 6).
Any ACME client with a DNS plugin for your DNS provider works (e.g. `acme.sh`, `lego`, `certbot`).
Renew automatically (certificates are short-lived).

Where to put the files:
- Portal: `/data/certs/portal.crt` (PEM, full chain) + `/data/certs/portal.key`. A watcher reloads nginx within ~10 s after a change.
  Fallback order: legacy `/certs/fullchain.pem` + `privkey.pem`, else a self-signed certificate. Pulling from a certificate API is planned.
- Routers: `/data/certs/router.crt` + `/data/certs/router.key`; routers fetch them via the scheduler from the generated script (section 6.1).

Verify:
```
openssl s_client -connect portal.example.com:443 -servername portal.example.com </dev/null | openssl x509 -noout -subject -dates
/certificate print detail where name=guest-portal
```

## 9. Rollout order and final end-to-end test

1. Worksheet filled; admin UI: site + router (router IP, secret) created.
2. Central instance running; certificate valid; `https://portal.example.com` reachable from the
   central LAN.
3. Per site: sections 2, 3, 4, 5 (guest SSID gets an address, internet works **without** hotspot
   first, isolated from LAN).
4. Per site: section 6 (hotspot, script, hotspot pages), then section 7 firewall rules if not done.
5. Phone test: join SSID -> captive popup -> portal -> login -> internet; check
   `/ip hotspot active print`. Open the hotspot name again: the portal status page with usage; "Log out" ends the
   session (gone from `/ip hotspot active print` within seconds), the login page shows "You have logged out".
6. Revoke the grant in the admin UI -> the session disappears within about a minute
   (`/ip hotspot active print`), proving Disconnect works.
7. Repeat on the second site, and test roaming between a legacy and a wifi-package AP if mixed.

## 10. Troubleshooting

| Symptom | Likely cause | Check / fix |
|---|---|---|
| Phone gets no IP | VLAN 30 missing on a hop, `vlan-filtering` without tagged entry, DHCP server on wrong interface | `/interface bridge vlan print`, `/ip dhcp-server print`, check tagged on trunk and CAP bridge |
| Phone gets IP but no captive popup | Hotspot not on `vlan-guest`, DNS not via router, firewall input drop blocks hotspot ports | `/ip hotspot print`, `/ip hotspot host print`; test a plain `http://` address; check dynamic hotspot rules |
| Redirect goes to router default page ("Hi, g..." status, default logout or login page) | Hotspot pages (`login.html`, `status.html`, `logout.html`, `alogin.html`) not uploaded / wrong `html-directory` | `/file print where name~"(login\|status\|logout\|alogin).html"`, `/ip hotspot profile print`; re-run the fetch block of step "Hotspot pages" |
| Certificate warning on hotspot name | Wrong/expired certificate, name not in certificate, profile `dns-name` mismatch, certificate not imported with key | `/certificate print`, `dns-name` must match `*.guest.example.com` |
| Router certificate not updated | Download denied: wrong token (re-paste script after regenerating), request not from the router IP (NAT, `src-address`), portal certificate not trusted (`check-certificate=yes`), files missing on the instance | `/log print where message~"guest-portal"`, instance log "Router certificate download denied", `/system script run guest-portal-cert` |
| Certificate warning on portal | Self-signed fallback active, wrong name, chain missing | Put `portal.crt` + `portal.key` in `/data/certs` (reload is automatic) |
| Portal page does not load before login | Walled garden missing, DNS rebinding filter, firewall drop | `/ip hotspot walled-garden print`, static DNS entry (8.1), forward rule 2 (5.4) |
| Login returns to login page / "RADIUS timeout" | UDP 1812 blocked, wrong `address`, secret mismatch, router IP unknown to portal | `/radius monitor 0 once` (timeouts), `/log print where topics~"radius"`, portal RADIUS log, `tcpdump` on the instance |
| Rejected although credentials fresh | Token expired (~60 s), MAC mismatch, site not allowed for the grant | Portal audit/RADIUS log; retry from the start |
| router IP mismatch | masquerade/srcnat on the VPN or central router, `src-address` not set | Section 7.1; add a srcnat exception (`action=accept` for UDP 1812/1813/3799) above masquerade |
| Disconnect-NAK, Error-Cause 406 (Unsupported-Extension) | RouterOS 7 hotspot accepts Disconnect only with `Framed-IP-Address` (User-Name / Acct-Session-Id are rejected). The portal sends only `Framed-IP-Address` from accounting (v0.12.6) | Instance log "RADIUS Disconnect-Request"; "not sent: Framed-IP-Address of the session unknown" = Accounting-Start without IP; "stopped or stale" = no recent accounting update (IP may be reused). Manual test: `echo 'Framed-IP-Address=<GUEST_IP>' \| radclient -x <ROUTER_IP>:3799 disconnect <SECRET>` |
| Guest DNS/ping/Disconnect blocked, portal name not resolved | Assistant firewall rules appended after an existing drop rule (e.g. defconf "drop all not coming from LAN") | `/ip firewall filter print where chain=input \|\| chain=forward`: the `guest-portal:fw:` rules must come before any drop rule; re-run the firewall block of the assistant (v0.12.6 moves them to the top) |
| Disconnect does nothing | Router not accepting (`/radius incoming accept=no`, port not 3799), UDP 3799 blocked on router input or tunnel, source of Disconnect differs from `/radius address`, wrong secret | `/radius incoming print`, input rule 5.3, central firewall 7.2, `tcpdump` UDP 3799 |
| Session not removed after grant end | Scheduler (`portal:enforce-grants`) not running, Disconnect failing | Instance logs; see previous row |
| Guest can reach LAN / router | Forward/input drop rules below an accept rule, interface list member missing | `/ip firewall filter print stats`, `/interface list member print` |
| Guests see each other | Client isolation off | Datapath: `client-to-client-forwarding=no` (legacy) / `client-isolation=yes` (wifi) |
| Works on one site, not on the other | Overlapping subnets, missing return route to the guest/router subnet on the central side | Routes and tunnel allowed networks both ways |
| Mixed sites: SSID only on some APs | Provisioning rule only in one CAPsMAN system | Section 3.4: configure both systems |

## 10a. Troubleshooting first setup

Findings from a first real setup; the setup assistant shows the same checklist.

1. **No DHCP for guests although the VLAN interface exists.** The "bridge" in the assistant was a new,
   empty bridge. It must be the bridge that contains the trunk port to the CAPs (usually the LAN bridge):
   ```
   /interface bridge port print where bridge=<BRIDGE>      # must list the trunk port
   /interface bridge print where name=<BRIDGE>             # vlan-filtering yes/no
   /interface bridge vlan print where bridge=<BRIDGE>      # only with vlan-filtering=yes: VLAN 30 tagged on bridge + trunk
   ```
   Move the VLAN interface: `/interface vlan set [find where name=vlan-guest] interface=<LAN_BRIDGE>`.
2. **Portal name resolves to the router.** The hotspot host name was set equal to the portal host name,
   so the static DNS entry pointed the portal name at the router. Use two names (e.g.
   `hotspot-a.guest.example.com` for the router, `portal.example.com` for the portal); the admin UI now
   rejects equal names. The same happens when the site setting "Portal IP" is the guest gateway: it must
   be the portal instance as reachable from the router (usually empty = instance IP for RADIUS); the
   admin UI rejects the guest gateway and addresses inside the guest subnet.
   ```
   /ip dns static print where comment~"^guest-portal:dns:"  # hotspot name -> guest gateway, portal name -> CNAME -> portal IP
   ```
3. **Code and SMS logins fail, MAC whitelist works.** Until the router certificate is imported the
   hotspot profile has only `login-by=mac`. Order: (1) portal certificate, (2) router certificate pulled
   in the portal, (3) router script (certificate script) on the router, (4) hotspot pages upload,
   (5) verify:
   ```
   /certificate print where name~"guest-portal"
   /ip hotspot profile print where name=guest-portal         # expect login-by=https,mac and ssl-certificate
   /file print where name~"(login|status|logout|alogin).html"
   ```
4. **Certificate re-imported on every run / rename fails.** Older script versions imported the chain
   with `name=guest-portal-new`, which creates several certificates (leaf and CAs) and broke the rename
   and the name-based fingerprint check. Paste the current router script again; it compares the
   certificate referenced by the profile and cleans up by name (section 6.1).
   ```
   /system script run guest-portal-cert
   /log print where message~"guest-portal"
   /certificate print detail where name~"guest-portal"
   ```
   v0.12.2 failed at step `cleanup before import` with `bad parameter comment`: RouterOS certificates
   have no comment. Paste the router script of v0.12.3 or later again.
5. **CertWarden pull: HTTP 404 / 401.** The server URL must be the server address only
   (`https://certs.example.com`), not the UI URL (`.../certwarden` or `.../certwarden/app`, removed on
   save); the admin UI shows the resulting download URL. Enter the certificate API key and the private
   key API key in their own fields (sent as `<certificate key>.<private key key>`). 404: check the server
   URL and the certificate name; 401/403: check both keys and their order.

## 10b. Removing the portal from a router

Setup assistant, section "Remove everything again", generates the script. It removes, by name or comment
`guest-portal`, in this order: certificate script + scheduler, hotspot server, hotspot profile, walled
garden (host + IP), `/radius` entry, imported certificates (comment `guest-portal`, plus the exact names
`guest-portal`, `guest-portal-ca-*`, `guest-portal-import*`, `guest-portal-new`, `guest-portal-new_*`
of older versions; other certificates such as `guest-portal.example.com` stay), static DNS entries,
DHCP option 114 (only option `captive-portal` with comment `guest-portal`; its reference in the guest
network is cleared only if it is the only option, otherwise a hint is printed), firewall rules and address
lists of the assistant. It is safe when entries do not exist and logs out connected guests.
- `/radius incoming set accept=no` is only a commented hint (no comment on that menu; other uses).
- The hotspot pages (`login.html`, `status.html`, `logout.html`, `alogin.html`) are not removed automatically (the
  html directory may be shared with other hotspots).
- Optional blocks: the RouterOS container (veth, bridge, mounts, envs; data on the disk stays) and the
  guest network infrastructure (Wi-Fi configuration, DHCP server/network/pool, gateway address,
  interface list `GUEST`, bridge VLAN entry, VLAN interface): run a line only if it was created for the
  guest network. Remove `cfg-guest` from the CAPsMAN provisioning slave list first.
- Firewall rules created by assistant versions before 0.12.1 use comments `guest: ...`/`portal: ...`;
  the script lists print commands for them.
- In the portal afterwards: delete the router (site page, Routers) or the whole site; this removes the
  RADIUS secret and the certificate token.

## 10c. Router state query (read-only API)

Optional, per router (site page, Routers, "Router API"); the API access is local to the instance (not replicated via federation, encrypted with APP_KEY): the setup assistant reads the router
configuration (print only) to check its blocks and to prefill empty inputs.
1. Router certificate first (sections 6 and 8): the certificate script imports it as `guest-portal`.
2. On the router: the block "Read-only API access" of the router (setup assistant, "Router state") adds
   group `guest-portal-ro` (policy `read,api,rest-api`; no write, no `sensitive`, so secrets stay hidden)
   and the user; replace `<API_PASSWORD>`. Set the certificate on the service you use (not done by the
   script, `/ip service` is not its own object):
   `/ip service set www-ssl certificate=guest-portal disabled=no` (REST, port 443) or
   `/ip service set api-ssl certificate=guest-portal disabled=no` (API over TLS, port 8729).
   Optionally restrict the user to the portal instance (`address=<INSTANCE_IP>/32`) and the service
   (`/ip service set ... address=<INSTANCE_IP>/32`).
3. In the portal: API host (router IP), type, port, user and password. TLS is trusted only by the
   pinned public key: by default the router certificate managed by the portal; another certificate on
   the service needs its pin (`sha256//<base64>`, e.g.
   `openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64`).
   After a rotation of the router certificate with a new key the query fails with a TLS error until the
   router imported the new certificate (certificate script, daily).
4. "Query state" (per router) or "Refresh" (all routers): per block present / missing / differs (value
   expected by the assistant vs. router) / legacy (created by an older version, updated on the next run) /
   name taken (no comment: created by versions 0.6.0 to 0.12.6 or by hand without the comment key; run the
   shown one-time adopt commands, then query again).
   The commands are greyed out while a router with API access has no query newer than 15 minutes
   (`PORTAL_ROUTER_STATE_MAX_AGE`) or than the last change of the inputs.
5. Uninstall: the block removes the user and the group; set the service certificate back first.

### 10d. Outdated routers ("Update router")

The portal notices when a router's hotspot pages or configuration no longer match what it generates now
(v0.30.0). The router never fetches anything by itself; the admin pastes the shown command.
- **Hotspot pages:** every page a router fetches (`/router-login/<router>/<page>.html`) is recorded with a
  fingerprint and the time. A page whose current content differs (portal URL, site id changed) or that was never
  fetched is outdated. Pages fetched by versions before 0.30.0 have no fingerprint: run the fetch block once.
- **Configuration** (routers with API access): the stored router state is compared like on the setup page; a block
  with a differing, legacy or missing object is outdated. The optional RouterOS container block counts only when the
  container is installed. A state older than the last change of the inputs is "check pending", not outdated.
- **Scheduled check:** `portal:router-state-check` at 06:17 and 18:17 (container time zone UTC) and once after a
  portal update (container start), queries every router with API access that this instance serves, one after
  another, read-only. Two failed queries in a row mark the router "unreachable since ...".
- **Display:** dashboard (one line per router, admins only), site page and setup page ("Update router" with the fetch
  block and the outdated command blocks; the router script as a link to its page).
- **Notification:** when a router becomes outdated, and again when it becomes unreachable, one message goes to every
  enabled notification channel (Telegram, Gotify, webhook event `router_outdated`) with a link to the commands. No
  further message while it stays outdated; once up to date again (new fetch or a fresh state), the next change is
  notified again.
